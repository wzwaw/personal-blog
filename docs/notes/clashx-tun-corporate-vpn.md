# 我一直在改 Clash 规则，根因却在“设置为系统代理”那一栏

> 文中的域名、DNS 地址和网段均为脱敏示例，不对应真实环境。

## 一个自相矛盾的现象

那几天我需要同时满足两件事：公司内网只能通过公司自己的 VPN 访问，而日常调试又必须让 ClashX Meta 开着 TUN。单独开 VPN，内网后台正常；一旦把 ClashX 也打开，后台就只剩浏览器里那句 `ERR_CONNECTION_TIMED_OUT`。

作为前端，我第一反应几乎是条件反射：控制台里写着连接超时，那要么是后端挂了，要么是我哪条代理规则写歪了。前者很快被同事排除，于是我就一头扎进了第二个方向——现在回头看，那句超时其实只说明连接没建起来，至于断在解析、路由还是握手，它什么都没交代。

最早让我警觉的其实不是超时，而是另一个细节。我在 macOS 网络设置里把公司域名加进“忽略代理的域名”，页面立刻就恢复了，可过一会儿那几行又自己消失。那张列表被别的东西持续重写——Clash 在接管系统代理时会把自己的配置整体写回去。当时我只把它当成一个需要绕开的麻烦，事后看，这个细节已经指向了根因：系统代理一直是开着的。

## 第一个假设：规则写错了

最顺手的动作是给公司域名加一条直连，并且放在 `RULE-SET`、`GEOIP` 这些宽泛规则前面：

```yaml
rules:
  - DOMAIN-SUFFIX,corp.example,DIRECT
```

Clash 日志确实显示命中了这条规则，页面照样打不开。我反复检查规则顺序、通配写法、有没有被订阅更新覆盖，又试着把公司网段补成 `IP-CIDR` 规则，折腾了很久，超时的样子一点没变。

我在这里犯的错，是把 `DIRECT` 读成了“绕过 Clash”。它真正的含义窄得多：这条连接不交给远端代理节点。至于连接从哪块网卡发出、要不要进公司 VPN，规则本身一个字都没说。日志里那句“命中 DIRECT”回答的问题，和我心里想问的问题，压根不是同一个。

## 第二个假设：DNS 或 Fake-IP 在捣乱

TUN 模式默认用 Fake-IP，应用先拿到 `198.18.0.0/16` 里的合成地址，系统自然无法按公司网段选路。于是我把公司域名后缀排除出 Fake-IP，又用 `nameserver-policy` 把它交给公司 DNS，顺手还把公司 DNS 和内网网段写进了 TUN 的排除地址。

改完再查，`dscacheutil` 返回的是正确的内网 IP，HTTPS 证书也没问题。我还顺手在 `/etc/hosts` 里把域名钉死到那个 IP，想看看是不是解析结果在某个环节被偷换——页面依旧打不开。hosts 只是在查 DNS 之前插了一脚名字解析，它管的是“域名换成哪个 IP”，换完之后这个包往哪走，它一点都管不着。到这里名字解析这一层已经干净了，故障只可能在更下面——连接从哪里出去。

顺带纠正我当时的一个想当然：开系统代理并不意味着 DNS 一定被接管。浏览器走 HTTP 代理时通常把域名原样交给代理、由 Clash 去解析，但本机的 hosts 和系统 DNS 依然各司其职。解析正常和路径正常是两件独立的事，我却拿前者去证明后者。

## 一组对照实验把问题钉住

真正有用的是两条只差一个变量的 `curl`：

```bash
curl -vkI https://admin.corp.example/
curl -vkI -x http://127.0.0.1:7890 https://admin.corp.example/
```

同一台机器、同一个域名、同一条公司 VPN，直连走完 TLS 握手拿到 HTTP 200；只是在前面套上 `127.0.0.1:7890`，就卡在 TCP 阶段超时。这一下把嫌疑范围砍掉了一大半：服务器活着，VPN 通着，证书没事，只有“先经过本地 Clash”这条路径是坏的。

Clash 日志把话说得更明白。它显示这次请求命中了 `DIRECT`，解析出的也是正确的内网 IP，可 TCP 连接超时；同一份日志里还写着它的默认出口接口是 `en0`。而我用 `route -n get` 查那个内网 IP，系统给出的 interface 是公司 VPN 的 `utun4`。顺带一提，`route` 只会告诉你本机为这个目标选的出口接口和下一跳，再往后的互联网路径它不负责，但眼下这一跳已经够用了。

矛盾终于摆到了台面上：系统认为该走 `utun4`，Clash 认为该走 `en0`。问题从模糊的“Clash 和 VPN 冲突”，收敛成了具体的“谁在发起这条连接”。

## 根因：两个入口叠加，换掉了发起者

系统代理和 TUN 根本不在同一层。系统代理是应用层的约定，浏览器主动去连本地的 `127.0.0.1:7890`；TUN 和公司 VPN 都在网络层接管 IP 数据包。两者同时开着，浏览器走的是前者：请求先到本机 Clash，Clash 匹配到 `DIRECT`，然后以自己的身份新建一条到内网 IP 的 TCP 连接。

要命的是封装和选路发生的时机。内核为这条新连接发出第一个 SYN 时，就已经在查路由表、决定出口接口、决定要不要交给某个 `utun` 做加密封装——这些都发生在连接建立的过程中，而不是连接建成之后再补。Clash 用默认物理接口 `en0` 发起，这条连接从诞生那一刻起就没进过公司 VPN，后面再也拐不回去。TUN 的排除网段在这里也帮不上忙，因为浏览器连的是 `127.0.0.1`，那段配置根本没被用到。

关掉系统代理后，链路就顺了：浏览器拿到真实内网 IP，直接 `connect`，内核查路由表，公司网段命中 VPN 的 `utunN`，加密后的外层包再由 `en0` 发出去。`utun` 和 `en0` 从来不是二选一，内网流量是先进 `utun` 封装、再借 `en0` 出门。

## 最后留下的东西

稳定组合很朴素：公司 VPN 开，ClashX TUN 开，“设置为系统代理”关。配置里真正必需的也只有几行示意：

```yaml
dns:
  fake-ip-filter: ['corp.example', '*.corp.example']
  nameserver-policy:
    '+.corp.example': [10.0.0.53]
tun:
  route-exclude-address: ['10.0.0.53/32', '198.51.100.0/24']
```

前者让公司域名拿到真实 IP，系统才有依据选路；后者把公司网段还给 macOS 路由表。网段要以 VPN 连上之后的实际路由为准，别想当然写 `10.0.0.0/8`；这些改动也要放进 Mixin 或覆写配置，否则订阅一更新就被冲掉。

排查顺序我也固定了下来：先只开 VPN 建立基准，确认目标本身可达；再看域名解析出的 IP 对不对；然后 `route -n get` 目标 IP，看系统打算从哪块网卡出去；接着用直连和显式代理两条 `curl` 做对照；最后回头 `scutil --proxy`，确认自己是不是同时开了两个入口。

这次真正救我的不是多加规则，而是设计了一个只差一个变量的对照。配置文件只会告诉你它被写成了什么样，只有对照实验会告诉你包实际去了哪里。
