# 从脚本到桌面工具：一次批量发布的工程实践

当一个应用需要上传、填备注、提审、等待审核，再发布时，手动操作还算容易。当同样的流程要在百余个小程序上重复，麻烦就开始变化：记不住谁已经完成，网络失败容易遗漏，审核跨了一天之后，还得重新确认每个版本的状态。

我最初希望让 AI 帮忙跑完这些重复动作。后来，它从一份 Skill 和几个脚本，长成了一个能管理登录、执行批次、保留进度的桌面工具，还加上了多套实时图形背景。

这次实践让我更在意两件事：**一个脚本需要补上什么，才能交给别人使用；AI 写出代码之后，用什么判断它确实有效。**

本文根据项目技术复盘整理，业务清单、内部接口、账号信息和本地路径已省略或通用化。文中的实现与观察对应当时版本。

## 先把“跑一遍”变成“可以继续跑”

最初的人工流程是：

```text
选择应用 → 上传代码包 → 填写备注 → 提交审核
    → 等待审核 → 核对结果 → 发布 → 下一个应用
```

这里有两种等待：网络请求的短等待，以及审核跨天的长等待。只要中间停下来，单纯的点击自动化就无法回答“下一次从哪里继续”。

因此，工具的目标逐渐明确：完成过的阶段有记录，失败能定位到单个应用，中途退出之后能恢复；使用者也不用反复复制登录凭据、查接口、记命令行参数。

“点一下批量执行”只是入口。实际需要管理的是每个应用在上传、提审、发布三个阶段的状态，以及本地记录与平台真实状态之间的差异。

## 桌面形态承接了哪些职责

这个场景既需要平台登录态，也需要读取本地代码包和配置，还要让任务持续运行并保存进度。桌面应用把这些能力放在了同一个运行环境中。

这并不意味着网页、插件或脚本做不了类似工具，只是它们需要采用不同的配套方案。对当时的使用场景，桌面应用比较容易收敛安装与操作步骤，代价则是安装包体积、系统适配和发行维护。

程序内部按职责拆成三块：

| 部分 | 主要职责 |
| --- | --- |
| 主界面 | 展示应用、版本、任务进度和错误，发送操作指令 |
| 主进程 | 管理会话、平台请求、任务队列与本地状态 |
| 平台窗口 | 加载开发者站点，供用户登录，并观察必要的状态查询请求 |

界面和主进程通过消息通信，接口类型集中声明，让两端的参数和返回值可以在编译时核对。业务判断留在主进程，界面主要负责展示和交互。

## 登录：让请求复用会话

早期脚本需要手工复制 Cookie。它能跑通流程，却把凭据维护变成了使用者的日常负担。

桌面版本改为打开正常的平台登录窗口，由用户扫码或完成验证。平台窗口和 API 客户端使用同一个持久化会话分区，后续请求由会话携带登录态。Electron 中，`persist:` 前缀表示持久化分区，同名分区复用同一会话，应用重启后仍可使用尚未过期的状态。具体语义见 [Electron Session 文档](https://www.electronjs.org/docs/latest/api/session#sessionfrompartitionpartition-options)。

这里省掉的是业务代码手工复制和拼接 Cookie 的过程。会话仍然属于应用的敏感数据，持久化也不代表凭据天然不可读取或已经加密。

登录有效性还需要在任务运行时持续判断。平台可能在会话过期后跳转到登录页，最终返回 HTTP 200 的 HTML；如果只看状态码，就会把它当成正常接口响应。

当时的实现结合状态码和最终响应地址识别失效，再停止继续派发任务、更新登录状态，并合并同一轮中的重复通知。对于其他平台，还需要区分权限不足和登录过期，按各自的响应约定处理。

平台页面运行的是外部代码，因此它与主界面的权限需要分别设计。原实现为请求捕获放宽过平台窗口的隔离设置，这是一项需要继续改进的取舍。后续应优先保留上下文隔离和沙箱，并校验消息来源、限制导航和暴露的方法；这些也是 [Electron 安全指南](https://www.electronjs.org/docs/latest/tutorial/security)强调的边界。

## 接口发现：先识别结构，再保存模板

某些状态查询缺少稳定的公开文档，路径又可能发生变化。项目采用了一种适配方式：观察平台页面正常发出的响应，根据审核中、已发布等字段识别候选查询，再把应用 ID 替换成占位符，保存请求模板。

模板保留请求方法、地址及必要的请求体结构。查询另一个应用时，再填入对应 ID。这样可以复用一次发现的结果，减少逐个应用配置的工作。

发现过程有几层来源：先观察用户打开版本页时产生的请求，再检查近期候选，最后尝试加载受限数量的版本页来触发查询。候选数量、存活时间、响应大小和等待时间都有上限，捕获失败也不能影响原页面。

这里有两个边界值得单独留下。

**响应形状也会变化。** 结构识别能减少对固定路径的依赖，但内部接口并没有因此变成稳定契约，模板仍需验证和失效处理。

**请求回放需要确认业务语义。** 原实现用方法和请求体做过筛选，但“没有请求体”无法证明请求没有副作用。推广这套方式时，应只回放已确认的查询操作，使用明确的允许列表，避免重复执行提审、发布或删除。

## 任务引擎：把失败当成正常分支

批量工具最重要的代码，往往写在失败之后。

### 重试前，先判断失败意味着什么

网络波动、限流、参数错误、审核未通过和会话失效，需要采取不同的动作。项目先在请求层分类，队列再按类别处理。

| 情况 | 处理方向 |
| --- | --- |
| 瞬时网络故障或部分服务端异常 | 在确认可重试后，有限次数等待再试 |
| 参数错误或业务条件不满足 | 记录原因，等待修正或条件变化 |
| 会话失效 | 停止派发，重新登录后继续 |
| 请求超时，远端结果未知 | 先查询状态，再决定是否重发 |

当时采用的是 `1s → 3s → 8s` 的预设等待序列。它适用于当时观察到的故障，不是所有平台都应该照搬的参数。

成功响应也要按契约解析。原项目遇到过已成功发布却返回空响应体的情况，直接执行 JSON 解析会误报失败；反过来，也不能把任意空响应或解析失败都当成成功。

### 并发需要按阶段决定

同一时间只允许一个批次运行，避免同一账号下的任务互相干扰。在批次内部，上传采用有限并发，提审和发布默认串行并保留间隔。

并发池让固定数量的 worker 持续领取下一个应用，减少分组执行时等待最慢任务的空闲。版本号、备注等公共参数则在启动前一次校验，避免每个应用重复报告同样的错误。

并发度最终要结合接口限制和实际负载确定。上传同样会改变远端状态，也需要考虑重复执行的结果。

### 本地跳过与远端核对一起使用

每个阶段都声明“什么情况下已经完成”，再次运行时跳过本地已成功的任务。它能处理很多重复点击和正常续跑，但还不构成端到端的幂等保证。

如果远端已经成功，本地却在写入结果之前崩溃，下一次启动时仍可能看到“未完成”。这时要查询平台状态，必要时结合远端提供的幂等机制，才能判断是否重发。

发布前重新核对真实状态也有同样的原因：上传与发布之间可能隔着一天，版本可能已经在后台被人工修改。本地资产 ID 是线索，发布目标需要以当时的平台状态确认。

用户点击停止时，工具不再领取新任务，让正在执行的任务尽量完成并保存结果。这种协作式停止可以减少中途打断带来的歧义，已经发出去的请求仍需等结果或随后查询。

## 状态恢复：记录进度，也保留诊断线索

每处理完一个应用，就保存阶段结果。写状态文件时，先写临时文件，再在同一文件系统内替换正式文件，减少程序崩溃留下半份 JSON 的风险。

这个做法解决的是文件替换完整性，不能单凭它保证断电后最近一次写入一定保留。远端操作和本地保存也不是一个事务，恢复时仍然需要处理结果未知的任务。

读到损坏文件时，原实现先改名归档，再重建默认状态。这样至少保留了后续排查和人工恢复的材料。日志则采用节流和固定容量缓冲，避免大量小写入；任务结果与普通日志采用不同的保存策略。

另一个容易忽略的问题发生在打包之后：开发时能通过相对路径找到的配套仓库，在同事电脑上未必存在。

项目为此设置了逐级回退：用户配置的路径、环境变量、常见位置探测，最后才使用内置清单快照。界面需要标注清单来源，因为内置快照可以帮助启动，却可能落后于真实配置。

这些工作直接决定了工具能否从作者的电脑走到另一台电脑。

## 实时背景：效果要放在合适的计算层

工具增加了五套主题，底层主要分成两类：二维程序化背景，以及包含小球碰撞和光照的三维场景。

| 效果 | 实现思路 | 主要成本 |
| --- | --- | --- |
| 液态金属 | 扭曲采样坐标，生成流动高光 | 每像素的迭代计算 |
| 网点波场 | 噪声与域扭曲，再做有序抖动 | 多层噪声采样 |
| 星域 | 网格哈希生成星点，叠加不同尺度的视差 | 邻域与多层求值 |
| 球池 | CPU 更新运动和碰撞，GPU 绘制实例化球体 | 碰撞检测、材质与绘制 |

二维背景主要由片元着色器从坐标算颜色，三维球池则使用 three.js 管理几何体、相机和材质。同一背景的配色变体可以复用计算逻辑，减少重复维护，但调色与合成本身仍有成本。

更重要的是前景可读性：背景亮度、遮罩和文本对比度要一起调整。主题切换还涉及组件库样式、CSS 变量、背景组件和原生窗口底色，漏掉窗口底色，启动或调整尺寸时就可能露出异色边缘。

成功、失败、警告这些状态色保持稳定，让装饰变化不影响任务判断。

### 一次卡顿，查出了三类问题

批量检查状态时，背景出现明显停顿。排查发现，数据更新、GPU 计算和资源生命周期都存在额外开销。

| 问题 | 调整 |
| --- | --- |
| 每完成一个应用，都向界面广播整张列表 | 改为发送单条变化，并保留未变化记录的引用 |
| 背景配置在每次渲染时生成新对象，触发资源重建 | 稳定配置引用，缩小组件接收的数据范围 |
| 着色器对每个像素重复进行九次采样 | 对照画面后，移除不必要的超采样 |

低优先级的列表更新也使用了 `startTransition`。它允许相关 React 更新被更紧急的更新打断，并不会把任意 JavaScript 计算搬到后台线程；用法与限制见 [React 文档](https://react.dev/reference/react/startTransition)。

此外，主题卸载时要清理帧回调、事件监听和图形资源。项目曾遇到注册和移除监听器时分别调用 `bind()` 的问题：两次得到不同函数，旧监听器没有被移除，连带保留了旧场景。

这次经验是先分清主线程、GPU 和资源重建各自的耗时，再决定改哪里。动画卡顿时，数据流同样值得检查。

## AI 开发：把验证条件提前准备好

这个工具的起点，是一次真实操作示范：让 AI 跟着走上传、填写备注和提审流程，观察请求与错误，再把已掌握的部分整理成 Skill 和脚本。

脚本让理解有了可执行的检验方式。能成功处理示范中的流程，说明这部分知识得到了验证；没有演示过的渠道、异常和状态，仍然需要在后续使用中补齐。

从脚本到应用，就是逐个消除“只有作者会用”的前提：手工复制凭据变成会话管理，命令行参数变成界面配置，结果文件变成阶段状态，常见错误变成可识别的原因和修复入口。

AI 对脚手架、类型、重复结构和明确逻辑的处理很快。困难集中在那些没有直接反馈的地方：画面是否出现了预期效果、批次是否会造成重复副作用、动画是否在真实负载下流畅。

文档里有一个很好的例子。球池材质加入了近似散射项，代码能编译，画面也好看。但后来做参数扫描和开关对照图时，发现其中一项在当时配置下几乎没有产生预期效果。

这说明“代码里存在这段计算”还不足以证明“效果已经出现”。参数对照让这个问题变得可观察，也让 AI 有机会根据结果继续修正。

以后再做类似工具，我会更早准备几类反馈：

- 用类型检查核对跨进程契约，减少参数和状态结构的偏差。
- 用真实响应样例验证成功、失败和结果未知等分支。
- 用恢复场景检查重启、停止和远端成功后本地未记录的情况。
- 用性能记录区分数据更新、渲染与资源重建的成本。
- 用固定条件的截图和参数对照检查视觉效果。

一次任务也尽量只设一个能验收的目标。例如先回答瓶颈在哪里，再修改具体开销；先确认响应含义，再决定重试。修正过的原因留在相关代码和流程入口，后续会话才能继续读到。

## 后续：让工具随着真实使用继续完善

下一步值得投入的，是状态与恢复机制的可验证性：哪些结果已经确认，哪些只是本地记录，哪些需要重新查询。接口适配、会话保护、安装签名和跨机器配置，也需要在扩大使用范围前继续完善。

协作时，可以把复盘中确认的接口差异、错误含义和设计决定沉淀到[知识库](/docs/knowledge-base-building)，让下次开发有据可查。推广则从小范围的真实批次开始，收集失败和恢复案例，再判断哪些能力适合抽成通用工具。

这次实践最有价值的收获，是逐渐知道该怎样验收一个工具：正常时能完成任务，失败时能解释原因，停下来以后知道怎样继续。AI 降低了实现成本，而这些判断依据，决定了生成的代码能否成为可靠的日常工具。
