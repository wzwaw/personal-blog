# 一条评论从手机到数据库：要不要先进消息队列

你在 App 里写下一条评论，点击发送，它几乎立刻出现在评论区。在这之前，这条评论要经过好几层系统才会被保存下来，每一层负责挡住一类问题。

这篇文章借一次真实的技术评审来讲这条路。一个面向普通用户的 App（行业里叫 C 端产品，C 指 Consumer）新上了评论功能，正在逐步开放给更多用户，这个过程叫放量。团队在群里讨论了不到一小时，起因是一个问题：用户发评论，是直接写进数据库，还是先放进消息队列再写？

讨论最后定下的方案是先进消息队列，同时让 App 先把用户自己的评论显示出来。本文记录到方案定下为止，改造上线后的效果还没有数据。

文中隐去了人员、表结构和业务名称。讨论里大家默认都懂的名词，我在第一次出现的地方补了解释。

## 一条评论要经过哪几层

一次“发评论”的请求从手机出发，到被保存下来，通常依次经过下面几层。开发者把这样一条路径叫作链路。

```text
客户端       手机上的 App
  ↓
WAF         接入层，拦截恶意请求
  ↓
网关         接入层，后端的统一入口
  ↓
评论服务      业务层，执行评论的规则
  ↓
消息队列      中间件，暂存等待处理的消息（评论要不要经过它，就是这次讨论的问题）
  ↓
数据库       存储层，长期保存评论
```

### 客户端

客户端是运行在用户设备上的程序，包括 App、网页和小程序。它负责界面，把用户的操作变成请求发给服务器。

客户端在用户手里，可能被修改，请求也可能由脚本伪造。所以它做的检查只能当作给用户的提示，服务器必须自己再检查一遍。

### WAF

WAF 是 Web Application Firewall 的缩写，中文叫 Web 应用防火墙。请求到达业务服务器之前先经过它。它检查请求的来源和内容，拦截已知的攻击手法，也能限制同一个 IP 地址在短时间内的请求次数。

IP 地址是设备在网络上的地址，可以粗略当作“请求从哪里发来”。

### 网关

一家公司的后端通常由很多个服务组成。客户端不直接访问它们，请求都先发到网关，由网关转给对应的服务。因为所有请求都经过这里，登录校验、限流、日志这类每个服务都需要的事情，也常放在网关上做。

限流指给单位时间内的请求数设一个上限，超出的请求直接拒绝。用户看到的通常是“操作太频繁”。

### 服务

服务是运行在服务器上的后端程序。后端常按业务拆开：用户、评论、审核各是一个服务，分别部署和升级。

评论服务负责和评论有关的规则：正文不能为空，不能超长，同一条评论不能重复提交。检查通过后，它把评论保存起来。

“不能重复提交”这条规则叫防重：同一次提交即使被发送了多遍，也只生效一次。

### 消息队列

消息队列（Message Queue，常缩写为 MQ）是一个独立运行的软件，用来在系统之间传递消息。发送方把消息放进队列，就可以去做别的事；接收方按自己的速度把消息取出来处理。放消息的一方叫生产者，取消息的一方叫消费者。Kafka、RocketMQ、RabbitMQ 都是常见的消息队列产品。

它自己不处理业务，夹在业务程序之间。这类软件统称中间件。

### 数据库

数据库负责长期保存数据。这个项目用的是 MySQL：数据存在表里，一条评论是表里的一行。把数据写进数据库，开发者常说“入库”。

一张表的数据越多，查询和维护就越慢。分表是把一张表拆成多张结构相同的表，每条数据按固定规则只进其中一张，常见的规则是用某个 ID 除以表的数量取余数。分库更进一步，把这些表分散到多台数据库服务器上。

## 当时的链路：直接写库

```text
客户端提交评论
  → 网关（高频 IP 拦截）
  → 评论服务：校验、防重
  → 写入数据库，等它写完
  → 返回“发送成功”
        └→ 往消息队列放一条消息 → 审核系统取走，开始审核
```

评论入库这一步是同步的。同步指发起方等这一步做完、拿到结果，才继续往下走：评论服务要等数据库写完，才告诉客户端“发送成功”。与之相对的是异步：发起方把任务交出去就继续，任务稍后由别人完成。

送审是异步的。评论要检查是否合规，这项工作由审核系统完成，比写库慢得多。评论服务只往消息队列里放一条“有新评论待审核”的消息，审核系统自己来取。两个系统不直接调用对方，一方变慢或暂时不可用，不会拖住另一方。这种关系叫解耦。

讨论中还提到了这些现状：

- 评论服务有防重，网关层有高频 IP 拦截。WAF 当时配置了什么，讨论里没有说，它出现在后面的待梳理清单里
- 评论表分了 100 张
- 评论正文的长度：客户端限制 500，服务端限制 2000，数据库字段是 `varchar(2000)`

## 第一个分歧：直接写库扛不扛得住

质疑的一方认为，评论入库应该先进消息队列，用它削峰。

削峰可以用一组假设的数字说明。假设数据库每秒能稳定写入 1000 条评论，而某一秒突然来了 5000 条：

- **直接写库**：5000 个请求同时去写。数据库来不及处理，多出来的请求只能等着。等待中的请求占着评论服务的处理能力，响应越来越慢，最后超时报错。严重时整个评论服务都变慢，连“看评论”也受影响。
- **先进队列**：5000 条先存进消息队列，评论服务马上返回。消费者按每秒 1000 条的速度取出来写库，5 秒写完。数据库一直按自己的速度工作，代价是这批评论晚几秒入库。

高峰被摊到了之后的几秒里，这就是削峰。

质疑的一方担心的不是正常流量，而是异常情况：客户端出了 bug 反复提交，或者 App 被破解后有人用脚本大量发请求。按 IP 拦截挡不住后者，因为攻击者可以租用大量 IP 轮流发送。

维护这条链路的一方给了三点理由：

1. 评论通常没有很陡的高峰。可以在放量过程中观察实际的 TPS 再决定。TPS 是 Transactions Per Second 的缩写，这里指每秒提交的评论数
2. 入库只是往一张表里写一行。先用限流兜底，以后要改成队列，成本也很小
3. 异步不等于防护。恶意请求同样会把队列塞满，限流仍然要做

第三点说的是消息队列的适用范围。队列能处理的是短时间的高峰：写入暂时超过数据库的处理速度，过后会回落。它不判断一个请求该不该被接受。大量恶意请求进了队列，正常评论就排在它们后面，入库越来越晚。判断请求该不该进来，要靠限流和防重。

分表也回答不了这个问题。分表控制的是单张表的大小。如果 100 张表仍在同一台数据库服务器上，这台机器每秒能承受的写入总量并没有变多。讨论里没有提到这些表分布在几台机器上。

那么链路为什么一直是同步的？原因在产品要求：评论发出后要立刻显示，一个内容下的第一条评论尤其如此。按当时的理解，改成异步后，评论要等消费者写进数据库才能被看到。产品没有接受这个延迟。

## 转折：立刻显示不需要等入库

有人指出，“用户立刻看到自己的评论”和“评论已经入库”是两件事。

客户端可以在发出请求的同时，把这条评论直接显示在本地的列表里，不等服务器的结果。点赞通常也是这样做的：按钮先变色，请求随后才发出。这种做法叫乐观更新，意思是先假定操作会成功，按成功的样子显示；万一失败，再撤回并提示用户。评论审核不通过时，同样是事后通知用户。

这样，产品要的“立刻显示”由客户端满足，服务端就可以改成异步。

还有一个附带的好处。“审核中”这类临时状态只需要存在于发评论的那台设备上，不必同步到用户的其他设备，服务端的代码会简单一些。代价是客户端和服务端的交互要重新约定。

## 第二个问题：正文到底能有多长

讨论中途转到了评论正文的长度。评审的人看到数据库字段是 `varchar(2000)`，第一反应是太长，接着要确认它和客户端的 500 是什么关系。

`varchar` 是数据库里存可变长度文本的类型，括号里的数字是最多能存多少个字符。这里容易混淆的是字符和字节。字节是存储空间的单位，一个字符占几个字节由编码决定。这张表用的编码是 utf8mb4，也就是完整的 UTF-8：英文字母占 1 字节，常用汉字占 3 字节，emoji 和少数生僻字占 4 字节。MySQL 里早期那个叫 utf8 的编码每个字符最多 3 字节，存不了 emoji，所以现在一般用 utf8mb4。

`varchar(2000)` 的 2000 是字符数，不是字节数。它能放下 2000 个汉字，最多占 8000 字节。

三层的上限用的计数单位并不相同：

| 位置 | 上限 | 计数单位 |
| --- | --- | --- |
| 客户端 | 500 | 字素簇：用户眼里的“一个字” |
| 服务端校验 | 2000 | UTF-16 码元：Java 的 `String.length()` 数的就是它 |
| 数据库字段 | 2000 | 码点：Unicode 给每个字符分配的编号 |

多数时候三者数出来一样，一个汉字在三种单位下都是 1。差别出在组合出来的字符上。一个由四个人组成的家庭 emoji，用户看到的是一个符号，所以是 1 个字素簇；它由 4 个人物 emoji 和 3 个连接符拼成，是 7 个码点；在 Java 的字符串里占 11 个码元。

三种单位之间没有固定的换算，这一点讨论里没有展开。500 个这样的 emoji 能通过客户端的检查，在服务端却是 5500 个码元，会被拒绝。正常的文字评论离 2000 很远，不会碰到这个问题。但如果要把字段改短，就得先决定以哪一层的单位为准。

字段是否改短，这次没有定论。

## 定下来的方案

提交链路改成：

```text
客户端提交评论，同时在本地显示这条评论
  → 网关：限流
  → 评论服务：校验、防重
  → 放进消息队列 → 返回“发送成功”
        └→ 消费者取出消息，写入数据库

用户刷新页面  → 显示服务端返回的评论列表
审核不通过    → 事后通知用户
```

送审原本就走消息队列，这部分不变。

另外，团队要把整条链路的性能和安全设计从外到内重新过一遍：WAF 的 IP 限流、网关的限流、哪些环节可以改成异步、数据库的限流保护、分库分表。放量期间继续观察实际的 TPS。

## 还没回答的问题

讨论到这里结束。下面第一条是讨论里明确提到的，后三条是我根据这个方案推出来的，要在改造时解决：

- **和客户端对齐交互**。接口返回的“成功”，含义从“已经入库”变成了“已经收下，稍后入库”
- **刷新后评论暂时消失**。如果用户在消费者写库之前刷新页面，服务端的列表里还没有这条评论。客户端要把本地这一条多保留一会儿，或者由服务端在列表里补上
- **写库失败怎么办**。同步写库时，失败可以当场告诉用户。异步之后，失败发生在用户看到“发送成功”之后，需要自动重试；重试后仍然失败，还要能通知到用户
- **正文字段是否从 2000 改短**，以及按哪种单位计数

## 每一层负责什么，管不了什么

| 层面 | 手段 | 负责什么 | 管不了什么 |
| --- | --- | --- | --- |
| 客户端 | 乐观更新 | 用户立刻看到自己的评论 | 评论是否真的保存成功 |
| 客户端 | 字数限制 | 输入时给用户提示 | 被修改或伪造的客户端 |
| 接入层 | WAF 按 IP 限流 | 拦截已知攻击和同一来源的高频请求 | 不断更换 IP 的请求 |
| 接入层 | 网关限流 | 控制进入后端的请求总量 | 单个请求是否符合业务规则 |
| 业务层 | 评论服务的校验和防重 | 拒绝空的、超长的、重复的提交 | 数据库写不过来 |
| 中间件 | 消息队列 | 削峰，让系统之间解耦 | 请求该不该被接受，以及长时间超出处理能力的流量 |
| 存储层 | 分表 | 控制单张表的大小 | 一台数据库服务器的写入上限 |

没有哪一层能单独挡住所有问题，所以团队最后要做的是把每一层重新过一遍，而不只是加一个队列。

这次讨论里让方案走通的一步，是把“显示”和“入库”分开。在那之前，同步写库一直被当成“评论要立刻显示”的必然结果。
