# 个人ai问答机器人

工作中总会遇到一些反复出现的问题：这个功能现在做到哪里了？某个字段为什么这样设计？一个规则是在需求里提过，还是已经落地了？

答案往往已经存在，只是散在项目文档、代码、历史决定和个人记忆里。每次有人来问，都需要重新找资料、确认版本，再组织一遍语言。

我想做一个小助手：同事在飞书里提问，它先找到对应项目的知识库，再根据材料回答；我在开发环境遇到需要协作的问题，也能沿用这套知识，整理出要向产品或后端确认的内容。

最近，我先把前半段接通了：一个在 Mac 上常驻、有人提问时才检索和调用 AI 的问答机器人。这里记录它背后的取舍与工作原理。项目名称、目录和示例内容均作了通用化处理。

## 先把想解决的问题拆清楚

刚开始，“把飞书接上 AI”听起来像是把两端连起来就行。实际思考之后，我发现中间至少有四个问题。

**第一，问题属于哪个项目？** 多个项目可能都有“配置”“策略”“报表”这样的词。同一个词，在不同项目里甚至有不同含义。必须先确定资料范围，再搜索答案；项目不明确时，问一句澄清比猜测更有用。

**第二，答案从哪里来？** 我希望复用已经维护的知识库，并核对它引用的代码。这样，新产生的决定能继续沉淀在原有资料里，机器人每次回答时再读取。

**第三，没有人提问时，它要做什么？** 我的需求是等待消息，因此可以让一个轻量的后台进程保持连接，收到问题后再启动 AI 任务。长连接的等待与模型推理，是两种不同的资源消耗。

**第四，它可以做哪些事？** 自动答疑的第一版只负责查资料、组织答案、回复原消息。联系其他同事、修改代码、更新业务数据，应当作为另外的工作流程，明确对象和操作范围后再执行。

这四个问题决定了第一版的形态：消息入口、项目路由、知识检索、AI 生成和回复发送，分别承担清楚的职责。

## 先认识几个角色

CLI 是 Command Line Interface，也就是命令行工具。它除了供人在终端里敲命令，也可以被另一个程序调用。

这次实现里，几个角色分别是：

| 角色 | 在哪里运行 | 负责什么 |
| --- | --- | --- |
| 飞书机器人 | 飞书中的对话入口 | 接受私聊或群内提问，展示回复 |
| 飞书 CLI | 本机 | 接收飞书事件，调用消息接口 |
| Python 后台程序 | 本机 | 判断项目、检索资料、排队和调度两种 CLI |
| 项目知识库 | 本机仓库 | 提供业务说明、实现边界和代码证据 |
| Codex CLI | 本机 | 把问题和材料交给云端模型，取回答案 |
| AI 模型 | 云端 | 根据传入的上下文生成回答 |

其中，Python 程序把整个过程串起来。机器人在飞书里有名字和头像，背后则是这些程序在协作。

## 一条问题怎样走完一圈

![个人 AI 问答机器人从接收问题到回复的工作流程](/images/personal-ai-qa-bot-flow.svg)

### 收到消息靠长连接

后台程序先启动飞书 CLI 的事件监听：

```bash
lark-cli event consume im.message.receive_v1 --as bot
```

命令建立与飞书服务器之间的 WebSocket 长连接。连接保持着，有新的消息事件时，飞书通过这条连接推送过来；后台程序等待事件到达。

飞书 CLI 将事件输出为一条条结构化数据。Python 读取这些数据，就能拿到消息正文、消息 ID、会话 ID、发送人，以及群消息是否真正 @ 了机器人。飞书官方 SDK 也提供了相应的 [WebSocket 客户端能力](https://github.com/larksuite/oapi-sdk-python/blob/v2_main/README.md#websocket-connection-host-and-handshake-headers)。

这里的“监听”，可以理解为程序一直守着一个消息入口。有消息时开始处理，没有消息时继续等待。机器人应用还需要配置相应的事件、权限和可见范围，群聊中也需要先加入机器人。

### 先选项目，再检索材料

假设有人问：“项目 A 的导出功能支持哪些筛选条件？”

程序先把“项目 A”映射到对应知识库，再查找导出、筛选条件等相关段落。若问题只写“导出支持什么”，且上下文没有说明项目，机器人就先问清楚。

第一版使用关键词和中文双字词匹配，挑选相关段落，再核对这些段落引用的源码片段。小规模、结构清楚的知识库，可以先用这种方式验证效果。

“先找资料，再把资料交给模型回答”是一种检索增强生成的思路，常被称为 RAG。这里的关键是把相关材料带进本次回答，向量数据库只是可能采用的检索工具之一。

知识库的组织也会影响效果。如果一段文字能清楚表达“目前实现了什么、什么还在计划里、依据在哪里”，机器人就更容易给出可核对的答案。把所有历史记录堆在一起，检索命中之后仍然可能读错含义。

### 脚本怎样把问题交给 AI

检索完成后，Python 会整理出类似这样的输入：

```text
当前问题：项目 A 的导出功能支持哪些筛选条件？

检索材料：
与导出有关的知识库段落。
相关代码片段及其核对结果。
当前读取的版本信息。

回答要求：
根据材料回答，区分已实现、规划和待确认事项。
关键结论附来源；资料不足时明确说明。
```

随后，程序启动一次 `codex exec`，把这份文本传进去。[Codex 的非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)支持从标准输入读取任务，并输出结果，适合被脚本调用。

“标准输入、标准输出”可以理解为程序之间传文本的入口和出口：Python 把准备好的文字写进去，Codex CLI 负责连接模型服务，再把生成的答案输出回来。实际调用还配置了执行限制，并关闭答疑用不到的命令、应用等工具。

本机这一版复用已有的 Codex CLI 登录。每个问题启动一个独立任务，带入本题材料；同一会话可以补充少量近期问答作为上下文。模型也需要获得必要上下文，才能理解追问中的“这个字段”指什么。

这也回答了我一开始的疑惑：常驻的是接收和调度程序，AI 任务在提问到来后才运行，完成后退出。

### 回复通过飞书消息接口发送

Python 取得答案后，再调用飞书 CLI：

```bash
lark-cli im +messages-reply \
  --as bot \
  --message-id om_example \
  --text -
```

这里的消息 ID 用来定位原问题，答案同样通过标准输入传给命令。飞书 CLI 使用已配置的应用身份，调用飞书开放平台的[回复消息接口](https://open.feishu.cn/document/server-docs/im-v1/message/reply)，把文字发回原会话。

因此，收消息和发消息是两条清楚的通道：接收事件走长连接，发送答案走消息 API。模型负责生成回答，实际发送由后台程序调度飞书 CLI 完成。

## 常驻程序怎样一直运行

在终端里启动脚本，只能证明这一刻能跑。要在关闭终端或聊天窗口后继续工作，还需要操作系统管理它的生命周期。

我使用 macOS 的 `launchd` 配置用户级 LaunchAgent，让程序在登录后启动，并在退出后按配置重新启动。苹果的[后台任务文档](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)说明了这类用户进程的启动和管理方式。

这次还遇到一个实际问题：脚本从开发工具里运行时可以读取项目目录，换成后台启动后，却被 macOS 的“文稿文件夹”权限拦住了。后来增加了一个具名的本地应用入口，由用户允许它访问 Documents，再启动 Python 工作进程。

同一份代码，换一个启动环境，文件权限、登录状态、环境变量都可能改变。因此，验证常驻服务时，需要在真正的后台环境里测试完整流程。

本机方案仍然依赖电脑保持运行和网络可用。电脑休眠或退出登录后，就无法及时处理新问题；恢复连接也不代表一定能补收离线期间的每条消息。

## 从能回答到能可靠地回答

第一次看到机器人回复，只验证了消息链路。要长期使用，还需要处理几类日常情况。

**重复消息。** 同一个消息事件可能再次到达。程序按消息 ID 保存处理状态，回复时再附上幂等键，也就是给同一次回复设置一个唯一标识，帮助平台识别重试，减少重复回答。若发送途中断开、无法确定是否送达，就把状态留为待核验，避免立即再发一遍。

**多个问题同时到来。** 第一版采用串行队列，避免瞬间启动很多模型任务。以后如果需要并发，也应先确定调用额度、排队时间和每个用户的频率限制。

**知识与代码已经变化。** 文档里写过某项能力，不代表它现在仍然成立。答案需要区分需求目标、前端已有、接口待联调和线上已验证；源码片段存在，也只能证明本地实现的一部分。

**不同人的上下文。** 项目范围、会话历史和资料权限要分别处理。一个人的追问不应混进另一个人的对话，能访问某份资料，也不自动意味着可以把它公开到所有群里。

这次已经在真实私聊中走通了“接收问题—按两个项目检索—调用 AI—自动回复”，并完成了消息去重、路由、会话隔离等程序检查。群内 @ 的处理已接入，仍需要真实群聊验证。这个阶段更适合把它当作一个有明确范围的个人答疑服务。

## 下一步可以怎样做得更好

### 让检索质量可以被验证

我会先收集一组真实问题，记录应该找到哪些资料、哪些结论必须出现、哪些地方应该回答“待确认”。再分别观察检索是否命中、答案是否准确、来源是否有效，以及耗时和调用消耗。

这样才能判断问题发生在哪一层：是资料没有记录、关键词没有命中，还是模型读到了材料却理解错了。对不同问题采取不同改进，比反复修改一大段提示词更容易核对收益。

知识规模变大、同义表达变多时，可以加入语义检索，与关键词检索一起使用；频繁重复的问题也可以考虑缓存。缓存要关联项目、资料版本和访问范围，知识更新或权限变化后及时失效。

### 让知识有版本，也有确认状态

以后可以把来源、适用项目、确认时间和状态整理成更稳定的元数据。回答时能够说明依据来自哪个版本，资料过期时也能提醒维护者。

机器人发现资料缺失时，可以先生成一份待补充清单。产品或后端给出明确答复后，由人确认，再更新知识库。经过确认的决定和临时聊天中的猜测，需要保留各自的身份。

### 提高在线能力，同时处理资料同步

如果使用范围扩大，可以把接收和调度程序迁到持续在线的运行环境，并为它配置独立的凭据、受控知识源和监控。

迁移时需要一起解决资料如何更新、哪些代码允许同步、访问权限如何继承、旧版本怎样退出。仅把脚本搬到服务器，并不能保证它回答的是最新事实。

### 把答疑与协作连接起来

当一个问题必须由负责人确认时，机器人可以进一步整理：现有证据是什么、哪里存在冲突、需要对方决定哪一点。用户指定本次对接对象后，再发起沟通，并将明确答复关联回原问题。

负责人可能变化，因此更适合结合当前任务动态确认对象。自动查询与对外发送、修改资料等操作，也应分别定义权限。这样，答疑和协作可以复用同一批知识，同时保持各自的责任边界。

## 怎样让更多场景复用这套流程

接通第一版之后，我更希望后续固定几种输入输出，让消息渠道、知识来源和模型执行方式可以分别替换。

| 可复用部分 | 固定什么 | 以后可以替换什么 |
| --- | --- | --- |
| 消息接入 | 用户、会话、消息 ID、正文 | 飞书、网页、其他工作入口 |
| 项目路由 | 问题归属与允许访问的资料范围 | 新项目及不同角色的规则 |
| 知识检索 | 返回材料、来源、版本与核验结果 | 本地 Markdown、受控在线文档、其他检索方式 |
| 模型调用 | 接收问题和证据，返回答案或明确失败 | Codex CLI、合适的 SDK 或模型 API |
| 回复与运行状态 | 原消息关联、处理状态、去重和日志 | 不同平台的发送接口与部署环境 |

例如，新增一个项目时，主要补上它的知识入口、别名和访问范围；换一个聊天平台时，主要调整消息接收和回复接口。模型调用方式变化时，项目知识库仍然可以继续使用。

现在，已有一部分约定被整理成可重复使用的技能说明，运行机制则放在独立后台程序中。技能说明负责指导怎么做，程序负责实际运行；两者继续保持清楚的接口，才方便在其他任务里复用。

我会把下一步放在真实问答的积累上：哪些问题反复出现，哪些资料总是找不到，哪些回答仍然需要人工纠正。把这些反馈带回知识库和流程里，这个小机器人才能随着日常工作逐渐变得有用。
