# 知识库搭建

做过几个需求之后，我开始遇到一种重复劳动：新需求看起来不复杂，但每次都要重新找页面、辨认同名字段、回忆上一次为什么这样处理，再去问产品和后端。

AI 能读需求，也能搜代码，但它未必知道应该把哪两处信息放在一起比较。同一个业务词，在不同模块可能对应不同的枚举；名字相似的页面，可能属于彼此独立的产品线；一段看起来奇怪的旧逻辑，可能承载着已经确认过的兼容要求。

我想搭建的知识库，就是把这些容易漏掉的联系留下来。经过一次真实需求和一次回放，我逐渐明确了它的定位：**帮助人和 AI 找到证据、发现差异、提出问题。最终结论仍要回到需求原文、当前分支代码，以及产品和后端的确认。**

本文根据一次业务知识库搭建与试用复盘整理，项目名称、目录、接口及具体业务规则已作通用化处理。

## 先确定什么值得记录

把需求文档、接口字段和代码说明全部复制进来，很快就会得到另一套需要同步维护的材料。代码变了，文档没有跟着变，AI 反而更容易拿旧说明当事实。

因此，我给知识库定了一条收录标准：**代码里能找到，但审需求时不容易主动想到去对照的内容，才值得额外记录。**

主要有这几类：

| 内容 | 要解决的问题 |
| --- | --- |
| 术语与枚举的差异 | 同一个名称或数字，在不同模块是否代表同一件事 |
| 模块地图 | 需求应该改哪套页面，哪些同名目录属于平行实现 |
| 能力差异 | 某个平台、应用或产品线，现在支持哪些能力 |
| 业务不变量 | 新需求没有明确要求时，哪些旧行为需要保留 |
| 决策与未决项 | 为什么这样做，谁确认过，还有什么没有确定 |

需求原文继续留在原文档里，字段和接口继续查代码及接口文档，实现经过继续看提交记录。知识库记录查找入口、差异和必要背景，让每一类信息都有清楚的来源。

遇到冲突时，也不能简单地认定某一方永远正确。需求描述的是目标，当前分支代码说明的是已有实现；两者不一致时，应该把差异列出来，确认这是不是本次要改变的行为。

## 一次返工暴露了知识库的真正难点

试用时，我用它检查了一次“给已有规则页面增加两个应用”的需求。

单看需求，似乎只是增加选项和筛选条件。实际对照后，问题分散在多个地方：同一应用在两个模块里的枚举值不同；几套同名页面没有共用实现；部分平台不支持这项能力；需求中的指标名称与已有页面不一致。

其中最有代表性的是指标名称。需求写的是 CPC，已有同类页面显示的是 CAC。知识库已经记下这个差异，并提示需要回问产品。但开发仍沿用了先前“按文档显示 CPC”的结论，没有把问题问出去。产品验收时要求改成 CAC，于是又返工了一次。

这件事让我意识到：**把正确的信息写进去，只完成了一半。流程还要确保它在做决定之前被读到，并且能推动一次明确的确认。**

当时还有一个实际问题：知识库文件在切换分支时被临时收起，开发结束后也没有及时更新。资料的存放方式影响了可用性，知识库自然也就脱离了日常开发。

后来，我用接入新应用之前的代码重新走了一遍分析流程。回放能更早提出指标名称、遗漏交互和接口过滤规则等问题，但它也有明显限制：知识库里已经包含落地后的答案，不能把这些答案算成提前发现。

所以，回放只用来检查流程有没有漏项。接口实际返回什么、某个字段叫什么、发布应该依赖哪条分支，仍然需要后端、联调和发布安排来确认。没有计时和独立对照，也就不据此宣称节省了多少时间。

## 用短入口组织知识，按问题读取细节

知识库的入口需要足够短，让人和 AI 能在开工时读完。具体内容再按问题拆开，避免每次任务都加载整份资料。

下面是一份通用目录示例：

```text
domain-knowledge/
  SKILL.md
  references/
    glossary.md
    module-map.md
    platform-matrix.md
    boards.md
    shared-filters.md
    invariants.md
    decision-log.md
  scripts/
    check-evidence.mjs
```

入口 `SKILL.md` 只说明：什么时候使用、先读哪些资料、如何核对、开工前确认什么、完成后怎么更新。详细内容各有职责：

| 文件 | 主要内容 | 读取时机 |
| --- | --- | --- |
| `glossary.md` | 术语、缩写、按模块区分的枚举 | 遇到名称或数字时 |
| `module-map.md` | 业务与代码目录的对应关系、平行实现 | 找改动位置时 |
| `platform-matrix.md` | 平台与应用的能力组合 | 判断支持范围时 |
| `boards.md` | 看板、表头、导出与汇总的关联 | 修改报表时 |
| `shared-filters.md` | 筛选字段在不同页面的含义、联动与提交方式 | 修改筛选时 |
| `invariants.md` | 兼容要求和应当保留的旧行为 | 列出改动后核对 |
| `decision-log.md` | 已确认的取舍、原因与未决项 | 需要解释“为什么”时 |

文件名可以随项目调整，关键是区分**现状**与**决策**。

现状页回答“现在支持什么、实现在哪里”，内容随代码更新。决策日志回答“为什么这样做、还有什么待确认”，保留必要的背景。同一主题发生变化时更新对应条目，减少互相矛盾的重复说明。

仅把目录建好还不够。使用的开发工具需要有明确入口，例如项目规则或 `AGENTS.md` 中的说明，让相关任务能稳定找到它。入口应指向流程，再按需读取细节。

## 用证据锚点发现过期内容

业务知识库最难维护的地方，是代码不断变化，而文字仍然看起来很可信。

为此，可以在现状页的关键结论后面附上证据锚点，再用一个只读脚本检查。下面只展示格式，路径和片段均为示例：

```text
〔证据 src/features/example/options.ts :: label: 'CAC'〕
〔证据无 src/features/example/options.ts :: label: 'CPC'〕
〔证据 src/features/example〕
```

三种标记分别表示：某个文件或目录中必须包含指定片段、必须不包含指定片段，以及某条路径必须存在。

锚点要选择能支撑结论的代码，最好包含具体条件与对应字段。一个随处可见的 `type` 或 `appType`，即使命中，也很难说明这句话仍然成立。

检查脚本还可以支持指定分支或提交。这样，同一份知识可以分别对照当前工作区、发布分支和历史起点。

**锚点通过，只说明预设的路径或文本条件满足，业务含义仍需结合上下文判断。** 锚点失效也可能有不同原因：实现改变了、文字过期了、代码搬家了，或者这项能力只存在于另一条分支。

因此，看到失败项后要回到代码检查。属于本次改动的，更新现状和证据；属于其他分支的，说明差异。不要为了让检查全部通过，删掉仍然有用的记录。

## 把知识库接进需求流程

知识库是否有效，最终要看它有没有参与日常决策。我把使用过程收成三个阶段。

### 开工时：先核对，再对照需求

先运行证据检查，知道哪些说明需要重新确认。再从需求中提取平台、应用、对象层级和字段，用模块地图定位代码，逐条区分：已经具备、部分具备、尚未实现，以及口径不同。

最后对照不变量，检查新行为是否会影响旧配置、历史数据回显、导出和相邻页面。

### 写代码前：把未决项交给能决定的人

整理结果时，固定保留五块：已有可复用、与现状不一致、需要修改的前后端、开工前需确认、跨页影响。

确认项再分给产品和后端。每条都写清三件事：需求怎么写、当前实现怎样、需要对方决定什么。

| 对象 | 常见确认内容 |
| --- | --- |
| 产品 | 指标显示名、文档遗漏的交互、功能范围、待定规则 |
| 后端 | 枚举值、接口路径、返回字段、筛选由哪一端负责 |

已经明确的内容无需反复询问。没有待确认项就直接继续；需要先按假设推进时，把假设及影响留在任务记录和未决项里。

尤其要检查同一次对话里早先形成的判断。如果后续代码证据与它冲突，就重新确认，避免最先说出的结论一直影响实现。

### 收工时：更新变化，再核对一次

业务口径发生变化后，更新相关现状页和证据锚点，在决策日志中记录能力变化、必要原因和剩余未决项，再运行检查。

纯粹的缺陷修复，如果没有改变业务口径，就不必新增一条日志。持续维护也需要控制体积，让下次使用者能够快速找到重点。

## 怎样判断它有没有帮助

早期可以先观察几件具体的事：是否更快找到正确模块，是否更早提出文档与代码的冲突，是否少了一次重复确认，以及需求落地后资料有没有同步更新。

如果要进一步评估，可以积累真实问题，记录应该找到的证据、应该提出的确认项和实际遗漏，再比较不同时间的表现。

知识库也有清楚的边界。它可以提醒接口需要验证，但实际响应要靠联调；可以记录上次的产品决定，但新场景仍可能需要重新拍板；可以说明某个提交有什么能力，但从哪条分支开发、与什么需求一起发布，要结合发布安排。

## 展望：协作、完善与推广

### 协作：让知识跟着需求一起维护

个人试用阶段，可以先把目录留在本地，验证结构和使用习惯。要走向团队共用，就需要把资料纳入共同维护的位置，并明确更新责任。

一个可行的起点是：需求开发者更新涉及的现状页，产品或后端确认对应口径，评审者核对证据与改动是否一致，再由明确的维护人定期检查发布版本。

这样，知识更新就能成为需求完成的一部分。AI 可以起草差异和更新建议，由相关人员确认后纳入。跨角色协作也更容易留下可追溯的结果：问题是什么、谁确认了、依据在哪里。

### 完善：从真实遗漏中补充内容

后续应优先补充那些反复引起误解、返工和重复调查的地方。某个模块目前记录很少，可以等真实需求暴露出缺口，再补上必要的口径。

同时，可以逐步增加确认时间、适用范围、来源和状态，让读者知道一条记录是已确认、待确认，还是需要重新验证。证据检查适合先做成提醒，等误报和分支差异处理稳定后，再考虑把明确、可靠的部分接入持续集成。

还可以维护一组真实问题作为检查样例，持续观察：有没有找到正确来源、有没有把假设写成事实、有没有漏掉应当询问的对象。每次修正都回到具体缺口，保持入口短、内容有用。

### 推广：先用一个模块证明价值

推广可以从业务边界清楚、需求较频繁的模块开始。先连续用几个真实需求，确认资料能够跟上代码变化，团队也愿意在收工时维护，再扩大范围。

分享时，最有帮助的是展示一条完整经历：原来容易漏什么，知识库让哪个问题提前出现，哪些部分仍然需要人工确认，以及维护付出了多少成本。

等流程稳定后，再提炼通用的目录模板、证据检查工具和评审格式，让其他模块按自己的业务补充。与[个人 AI 问答机器人](/notes/personal-ai-qa-bot)这样的入口结合，也可以让同事通过提问找到资料，并把没有答案的问题反馈给维护者；资料范围和访问权限需要随入口一起确定。

我希望这套知识库最终能够融入团队每天的工作：审需求时帮助对照，实现时提醒边界，收工时留下决定。让下一次参与的人和 AI，都能从已经确认过的知识继续往前走。
